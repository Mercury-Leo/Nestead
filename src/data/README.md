# data
The only way screens reach stored rows: the `Collection` and `DataStore` contract, the `Account` interface for sign-in and families, a shared row cache, and two backends.

## How it works
- A backend is a `DataStore` plus, for real sign-in, an `Account` whose `openStore()` builds it. `../auth/session.tsx` is the only place that picks one; the demo session builds `withCache(createLocalStore(...))`, and `../auth/openFamily.ts` builds `withCache(account.openStore(...))`.
- `supabase/` is the whole Supabase adapter. Swapping backends means a new folder beside it with the same two interfaces; the steps are in [ARCHITECTURE.md](../../docs/ARCHITECTURE.md#swapping-the-backend).
- `CachedCollection` runs at most one read at a time, queues one more for changes that arrive mid-read, applies `update` and `remove` at once and undoes them if the backend refuses (`cache.ts`).
- A collection nobody watches stays subscribed for `LINGER_MS` (30 s); `preload()` opens one before its screen mounts (`cache.ts`).
- On Supabase, `photos.url()` calls made in the same task are signed in one `createSignedUrls` request once its microtasks have run, and each URL is kept for 55 minutes. A screen of recipe cards costs one request, not one per card (`supabaseStore.ts`).
- Realtime echoes every insert and update back to the client that made it. `supabaseStore.ts` remembers the version each of its own writes returned and drops an echo carrying exactly that version, since `create()` and `update()` have already notified. A writer re-reads the table once per write, not twice.
- `loaded` is false until the first read, so a screen can tell "no rows" from "not read yet" (`useCollection.ts`).
- A failed read never counts as loaded. `failed` stays true until a read lands, and the rows stay as they were: none, before the first read. While the collection is open the cache reads again after 1, 2, 5 and 10 s, then every 30 s (`retryDelay()`), and at once when the browser comes back `online` or the tab is shown again (`onComeBack()`, `retry.ts`); `retry()` reads at once and shows Loading until that read lands or fails. Until 2026-10-10 a failed first read set `loaded` with no rows and was not retried, so the shopping list looked emptied until the next change arrived (`cache.ts`).
- Coming back to the tab after `AWAY_MS` (30 s) or more reads every open collection again, keeping its rows on screen meanwhile: realtime drops while a phone sleeps, and what changed meanwhile is never sent (`cache.ts`). On Supabase a channel that joins again after a drop also re-reads its table; its first join does not (`supabaseStore.ts`).
- Without a session supabase-js sends the publishable key in the member's place, and RLS answers a family read with no rows and no error, an empty list the cache would believe. So every row call, `readMembership()` and `readFamily()` call `requireSession()` first and throw instead, which the cache and the session retry. A read refused with "JWT expired" (a device clock behind the server's) also starts a session refresh before the next try (`supabase/signedIn.ts`).
- `preloadStore()` reads the board's and the kitchen's collections at sign-in, not `shows` or `taskCompletions`: the Shows page reads its collection, and History its own, when someone heads for the link (`preloadCollection()` from `../app/warm.ts`) or when first opened, and each lingers like any other (`cache.ts`).
- Local rows are one JSON array per key `nestead:<familyId>:<collection>`; other tabs hear of changes through the `storage` event (`local/localStore.ts`).
- The guarantees every backend owes are listed in [ARCHITECTURE.md](../../docs/ARCHITECTURE.md#collectiont).

## Rules & gotchas
- A new Supabase read, in a collection or the `Account`, calls `requireSession()` first, unless it is meant for someone signed out (`invite_family_name`): without it, a failing token refresh turns the read into an anonymous one that answers "nothing" (`supabase/signedIn.ts`).
- New backend work goes through the interfaces: add a method to `DataStore` or `Account` in `types.ts`, implement it in the adapter folder, and call it through the interface. Screens, `../auth/` and `../features/` never import an adapter, a backend SDK, or name a table or RPC. A rule the backend must enforce goes in the interface's doc comment.
- The `Account` doc comment in `types.ts` lists what a backend must enforce itself (member id is user id, one family per person, family-only visibility, one diet profile per family). The client relies on all four.
- The AI methods (`accessToken`, `aiStatus`, `clearAiKey`, `setAiModel`) come with their own list in `types.ts`, a `//` section comment above them (a second doc comment there would bind to nothing): only a family's members read or change its AI settings; no call returns the plaintext OpenRouter key, and the encrypted one comes only through the server's claim, for the caller's own family; free reads are counted atomically per user per UTC day and for the whole app; the plaintext key is never stored. `Account` has no method to store a key: the server encrypts it and stores it (`../../server/ai/`).
- `fail()` in `supabase/supabaseAccount.ts` throws `error.message` only, never PostgREST's `details`: a check-constraint error's detail carries the whole row, ciphertext included. Keep it that way for every RPC. (`set_family_ai_model` also checks the model itself and raises a bare `Invalid model`, since a caller outside the app sees PostgREST's details; `../../supabase/README.md`.)
- `supabase/familyAi.test.ts` runs against the project in `.env.test`, which is production. It stores a fake ciphertext before anything claims and removes it in `finally`, and never calls `claim_ai_request` without a key in place, since that spends one of the app's real free reads. It skips only when `family_ai_status` is missing (the migration is not applied yet; `migrationMissing()` decides, and has unit tests that run without `.env.test`); any other error fails it. Its test has a 30 s timeout so `finally` can remove the fake key.
- A patch value of `undefined` clears the field in both backends and the cache (`cache.ts` `merge`, `supabaseStore.ts` `toRow`, and a contract case).
- A screen that waits for `loaded` must also handle `failed`: `loaded` stays false for as long as reads fail, so Loading alone would spin with no way out. Show `<LoadFailed onRetry>` (`../components/LoadFailed.tsx`) for `failed && !loaded`, with `retryCollections()` behind it (`../app/AppRoutes.tsx`, `../features/board/BoardPage.tsx`, `../auth/accountSession.tsx`).
- `supabaseStore.ts` converts top-level keys only (nested jsonb keeps camelCase), reads NULL as absent, and throws on an `update` that matched no row, which PostgREST reports as success.
- PostgREST answers at most the project's Max Rows (1000 by default) per request and drops the rest without an error, so `supabaseStore.ts` `list()` reads pages of `LIST_PAGE` (1000) rows ordered by `id` until one comes back short; `taskCompletions` grows without bound. Keep `LIST_PAGE` at or below Max Rows, or a full page looks short and the read stops early.
- `supabaseStore.ts` re-serialises every timestamptz column through `Date` (`TIMESTAMP_KEYS`: `createdAt`, `updatedAt`, the shows' `fetchedAt` and `watchedAt`, and the tasks' `doneAt`), so it reads back as the ISO string the app wrote rather than Postgres's `+00:00` form. A new timestamptz column joins that set; a `date` column (`released`, `dueDate`) is already `YYYY-MM-DD`.
- `taskCompletions` rows outlive their task: nothing cascades from `tasks`, an entry's `taskId` is a plain id (no foreign key in Postgres), and Restore points entries at a re-created task with an ordinary `update`. The board creates and removes rows by id and never lists the collection; only History does (`types.ts`, `collection.contract.ts`, `../features/board/actions.ts`).
- `remove()` of a row that is already gone resolves in every backend: two devices auto-clearing the same old tasks both delete the same rows, and two unticks of the same tick both remove its history entry (`collection.contract.ts`).
- `shows` holds one row per `imdbId` per family. Supabase enforces it with a unique constraint; the local store does not, and relies on `addShow()` checking first (`types.ts`, `../features/activities/shows/actions.ts`).
- A show's `favorite` is absent on a new local row and `false` on a Supabase one (the column defaults to false and is not null), so read it as `favorite === true`. Unstar by writing `false`: patching it to `undefined` writes NULL there, which the column refuses.
- A show's `tags` is absent on a new local row and `[]` on a Supabase one (the column defaults to empty and is not null), so read it as `show.tags ?? []`. Remove the last tag by writing `[]`: patching it to `undefined` writes NULL there, which the column refuses.
- Another client's delete never arrives over realtime. The channel filters on `family_id`, and a DELETE event carries only the primary key, so the filter never matches. The deleting client still notifies its own listeners (`supabaseStore.ts`; measured in `../../docs/PERFORMANCE.md`). Other devices see the delete on their next read: a change of their own, a realtime rejoin, or coming back to the tab after 30 s (`cache.ts`).
- `localStore.ts` calls itself the only localStorage user, but `../auth/invite.ts` and `supabase/supabaseClient.ts` use it too.
- Photo ids are `<familyId>/<uuid>` locally and `<familyId>/<uuid>.jpg` on Supabase (`local/localPhotos.ts`, `supabase/supabaseStore.ts`).
- With all six `SUPABASE_TEST_*` values in `.env.test`, `npm test` runs the live suites, which delete every row in both test families between cases (`supabase/supabaseStore.test.ts`). They clear and test `shows`, `addresses` and `taskCompletions` too, so they fail until `../../supabase/migrations/20261004120000_shows.sql`, `20261004200000_addresses.sql`, `20261005120000_shows_favorite.sql`, `20261005130000_shows_genres.sql`, `20261005140000_shows_tags.sql` and `20261010120000_board_done_tasks.sql` are applied to that project.

## Tests
The contract runs three times: `local/localStore.test.ts`, `cache.test.ts` (cached local, plus seventeen cache cases; six of them fail reads: not loaded, the growing waits, Try again, rows kept when a later read fails, `online` and the tab shown again, and no retries once closed; one comes back to the tab after a moment and after 30 s), and `supabase/supabaseStore.test.ts` (live). Its shows case round-trips a release date, `fetchedAt`, a decimal rating, sets then clears `watchedAt`, moves to `dropped`, then stars and unstars the show; a second shows case keeps genres as a list, an empty list apart from none, and replaces it whole; a third keeps tags as a list, replaces it whole and clears it with `[]`; a task keeps `doneAt` and `completionId` and clears both with `undefined`; a history entry round-trips (Hebrew included), outlives its task and can be pointed at another; removing a missing row resolves. On Supabase they need `../../supabase/migrations/20261004150000_shows_dropped.sql`, `20261005120000_shows_favorite.sql`, `20261005130000_shows_genres.sql`, `20261005140000_shows_tags.sql` and `20261010120000_board_done_tasks.sql` applied. The Supabase suites run in the `node` environment, not jsdom. `boundary.test.ts` reads source files only. `supabase/signedIn.test.ts` runs the adapter against a stand-in client, no project needed: without a session it refuses to read rows, delete or read membership and sends nothing; "JWT expired" starts a refresh; `list()` returns all of 2,500 rows served 1,000 a request, and stops after a short first page; a realtime rejoin re-reads, a first join does not. `supabase/aiStatus.test.ts` maps `family_ai_status()` rows (with a key, free only, a setter who left, and a field it must not carry).
